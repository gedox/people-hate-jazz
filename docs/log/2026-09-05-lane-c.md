## How to get a browser in this lane

`preview_start` is refused in scheduled runs ("nobody is present to approve"). The pages need
no server at all: there is no `fetch`/XHR anywhere in `assets/js/`, so `file://` loads the real
CSS and JS. Headless Chrome from Bash is already sanctioned here — it is how the OG cards are
rendered; the standing order forbids running a *server* that way, not a browser.

Two gotchas, both already known to this repo:

- Chrome will not make a window narrower than ~485px, so **render the page in a sized
  `<iframe>`** inside a big window and measure/screenshot inside it. Media queries evaluate
  against the iframe, which is what you want.
- Flipping `[data-theme]` at runtime leaves `color-mix()` custom properties **stale** in Chrome
  — `--ink-faint` (a plain hex) updates, `--rule-hard` does not. Read from a freshly inserted
  clone, or paint the literal token definition, or you will measure yesterday's colour. This
  cost me two wrong readings before I caught it.

```bash
chrome --headless=new --disable-gpu --allow-file-access-from-files \
  --virtual-time-budget=15000 --window-size=1700,1300 --hide-scrollbars \
  --dump-dom "file:///…/probe.html?w=375&h=812&page=index.html&theme=light"
```

The probe iframes the page, then reports counts, real overflow, computed sticky geometry,
focus visibility, tap-target boxes, and contrast ratios composited through a canvas (which
handles `oklab()` and `color(srgb …)` — Chrome serialises `color-mix()` as both, and a
naive `rgba()` regex silently returns nothing). Screenshots use the same iframe trick with
`--screenshot`; force `.reveal` elements to `is-in` first, since setting `scrollTop` never
fires the IntersectionObserver and the page shoots blank.

## What I built

**`sell.html`** — a new, static, three-step listing form: verify email → describe the lot →
submitted-to-review confirmation. It's a real client for the endpoints #21 shipped:
`POST /api/auth/request-code`, `POST /api/auth/verify-code`, `POST /api/lots` with the bearer
token. Not a mock — if a dev/prod server is behind it, this genuinely files a pending lot.

Design decisions, against `.impeccable.md` and the mission's own framing of what a listing
flow needs to do ("if it feels like a tax form, nobody lists"):

- **One-time code, not a password** — matches M1 identity's explicit no-passwords rule, and
  is the actual mechanism `verify-code.mjs` implements.
- **No photo upload field.** The mission and `.impeccable.md` both forbid faking a product
  photo, and there's no upload/storage pipeline yet. Saying so as a form field, rather than
  quietly omitting it, is the honest version of "not built yet."
- **Trust surfaces built in, not bolted on** — a "no payment collected" strip above the fold,
  and a "how settlement works / if it goes wrong / who sees your email" section below the
  form, per the shift brief's #3 (trust surfaces are usually an afterthought; I put them at
  both ends of the flow instead of only at the bottom).
- **Reused the store's existing visual vocabulary** (`.bidfield`, `.spec`, `.sellmsg` mirrors
  `.bidmsg`) rather than inventing a second design language for one page.
- Errors are specific and non-alarming (`bidmsg`-style inline messages, not alerts), and the
  network-failure case explicitly says *why* it likely failed (viewing the static file, not
  the deployed API) rather than a generic "something went wrong."
