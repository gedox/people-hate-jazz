## What I built

**`sell.html`** — a new, static, three-step listing form: verify email → describe the lot →
submitted-to-review confirmation. It's a real client for the endpoints #21 shipped:
`POST /api/auth/request-code`, `POST /api/auth/verify-code`, `POST /api/lots` with the bearer
token. Not a mock — if a dev/prod server is behind it, this genuinely files a pending lot.

Design decisions, against `.impeccable.md` and the mission's own framing of what a listing
flow needs to do ("if it feels like a tax form, nobody lists"):

- **One-time code, not a password** — matches M1 identity's explicit no-passwords rule, and
  is the actual mechanism `verify-code.mjs` implements.
- **No photo upload field.** The mission and `.impeccable.md` both forbid faking a product
  photo, and there's no upload/storage pipeline yet. Saying so as a form field, rather than
  quietly omitting it, is the honest version of "not built yet."
- **Trust surfaces built in, not bolted on** — a "no payment collected" strip above the fold,
  and a "how settlement works / if it goes wrong / who sees your email" section below the
  form, per the shift brief's #3 (trust surfaces are usually an afterthought; I put them at
  both ends of the flow instead of only at the bottom).
- **Reused the store's existing visual vocabulary** (`.bidfield`, `.spec`, `.sellmsg` mirrors
  `.bidmsg`) rather than inventing a second design language for one page.
- Errors are specific and non-alarming (`bidmsg`-style inline messages, not alerts), and the
  network-failure case explicitly says *why* it likely failed (viewing the static file, not
  the deployed API) rather than a generic "something went wrong."

## Why a new file, not editing `store.js`

The store's entire SPA — routing, every screen's markup — lives inside `assets/js/store.js`,
which is Lane A's file (`docs/LANES.md`: A owns `assets/js/**`; C owns CSS and "markup
structure in any HTML"). There is no static HTML for the bid moment or outbid/won states to
go redesign — it's all JS template strings. I could not touch it without breaking the lane
boundary that exists specifically to stop collisions, so I built the seller flow as its own
page instead, which needed no such boundary-crossing. Its CSS went into `assets/css/store.css`
(mine) under a new `SELLER FLOW` section; `store.js` is untouched.

**This is worth the owner's attention:** the bid moment, outbid/won/lost states, and other
trust surfaces the shift brief asked about *also* live entirely inside `store.js`. Lane C
cannot design those without either a lane-boundary exception or Lane A extracting that
markup into templates C can touch. Filed below.
