# Lane A — 2026-09-05

## Mission workstream: M1 Persistence (+ a slice of Identity, Bidding, Handover)

Persistence was the furthest-behind workstream — `/api` had only `_lib/auction.mjs`
(rules, no I/O). Built the storage adapter and the server endpoints that make the
existing auction rules authoritative, per MISSION.md's design: one adapter interface,
swappable later, GitHub-JSON as the zero-new-account backend for now.

## What shipped

- **`api/_lib/storage.mjs`** — the adapter interface (lots, bids, accounts, one-time
  codes) plus an in-memory reference implementation. Every handler codes to this, never
  to a specific backend.
- **`api/_lib/github-store.mjs`** — the real adapter: reads/writes JSON files in this
  repo via the GitHub Contents API (`data/store/{lots,bids,accounts,codes}.json`).
  Writes are serialized per-file so two concurrent requests can't race on a stale `sha`.
  Untested against the live API (would need a token/repo in this session) — the
  interface is proven by 28 passing tests against the in-memory adapter it shares a
  contract with, but the GitHub-specific plumbing itself has not run for real yet.
  **Owner: before relying on this in production, do one real create+read+write cycle
  against a scratch repo/branch to confirm the Contents API calls are shaped right.**
- **`api/_lib/identity.mjs` + `api/_lib/mailer.mjs`** — email + one-time-code identity,
  no passwords. `mailer.mjs` is the human gate #2 adapter: today it's a console stub
  that logs the code (so the flow runs end-to-end and is testable), and it throws loudly
  if `EMAIL_SENDER_API_KEY` is set without an integration wired up, so it can't silently
  no-op once the owner picks a sender.
- **`api/_lib/session.mjs`** — HMAC-signed session tokens (node `crypto`, no library) so
  a bid can be attributed to a verified account rather than a client-asserted id.
- **Endpoints**, all plain `.mjs` handlers, node stdlib only:
  - `POST /api/auth/request-code`, `POST /api/auth/verify-code`
  - `GET/POST /api/lots` (GET is public/live-only; POST requires a session token, lands
    in `status: "pending"` — never straight live)
  - `GET/POST /api/lots/[id]/bids` (POST re-validates every bid against
    `api/_lib/auction.mjs`'s `placeBid` — the server is the only authority, per MISSION.md)
  - `POST /api/lots/[id]/approve` — moves a pending lot live and sets its close time.
    Gated on a shared `ADMIN_TOKEN` env var since there's no reviewer UI yet; this is
    the seat belt so a submission can never self-approve.
  - `POST /api/lots/[id]/settle` — runs `auction.mjs`'s `settle`/`outbidders` once a
    lot's clock has run out, marks it closed, returns the outcome and who to notify.
- **28 new tests** (`tools/test/storage.test.mjs`, `identity.test.mjs`, `session.test.mjs`),
  all passing, alongside the existing 13 in `auction.test.mjs` — 41 total, `node --test
  tools/test/` green.

## What's explicitly not done (next workstream picks these up)

- **The store UI still talks to `localStorage` only** (`assets/js/store.js`). Wiring it
  to these endpoints is real work — it changes the bidding UX from optimistic/local to
  request/response — and touching `store.js` logic is in-lane, but I judged it safer to
  land the server contract first, tested and reviewable on its own, than to bundle a
  UI rewrite into the same PR. Flagging as the next A pickup.
- No reviewer UI for `approve` (curl/Postman with `ADMIN_TOKEN` only, for now).
- Handover (`settle`) returns the outcome but doesn't notify anyone — that needs gate #1
  (project email address) before there's anywhere to send it from.
- `github-store.mjs` is unverified against the live GitHub API (see note above).
